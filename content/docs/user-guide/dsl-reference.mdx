SynthSpec is the language used in `.synth` files. This page documents every statement.

If you have not written a design before, work through [Your First Board](/user-guide/first-board) first — it introduces the handful of statements you actually need, in the order you need them. This page is for looking things up.

<Callout type="info">

An AI assistant connected to the [MCP server](/user-guide/mcp-server) can call `synth_language_reference` to get this grammar plus three complete example designs at runtime, so it never has to guess at syntax.

</Callout>

## The Short Version

In practice, most designs use six statements. Everything else on this page is for when you need it:

```rust
board "my_board" {                                   // 1. the board
  layers 2
  manufacturer "jlcpcb"

  group "POWER" color "#c2410c" {                    // 2. a labelled block
    component U1: regulator "ams1117_3v3"            // 3. a part
              value "AMS1117-3.3"
    notes "" { "5 V in, 3.3 V out." }                // 4. intent, in prose
  }

  connect U1.vout -> U2.vdd as "+3V3"                // 5. a wire, 6. a net name
}
```

## File Structure

A file contains zero or more `import` statements followed by exactly one `board` block. Everything else lives inside the board.

```text
[import "relative/path.synth"]*
board "<name>" {
  <statement>*
}
```

## Board Settings

These go directly inside the `board` block, conventionally at the top.

| Statement               | Required | Description                                                                                   |
| :---------------------- | :------: | :-------------------------------------------------------------------------------------------- |
| `layers <n>`            |   Yes    | Copper layer count. Must be `2`, `4`, or `6`.                                                 |
| `manufacturer "<name>"` |    No    | Fab profile whose rules are checked: `"jlcpcb"`, `"pcbway"`, `"oshpark"`, `"jlc-filled-via"`. |
| `revision "<tag>"`      |    No    | Revision tag for the schematic title block, e.g. `"A"`, `"1.2"`.                              |
| `company "<name>"`      |    No    | Design-authority name for the title block. Distinct from `manufacturer`.                      |
| `requires <process>`    |    No    | Declares a fabrication process the board cannot be built without.                             |
| `legends <on\|off>`     |    No    | Connector pin legends. Default `off`.                                                         |

```rust
board "my_board" {
  layers 4
  manufacturer "jlcpcb"
  revision "B"
  company "Acme Robotics"
}
```

Each of `layers`, `manufacturer`, `revision`, and `company` may appear at most once.

### `requires`

Declares a process the board depends on. Today `via_in_pad` is the only one — a via drilled inside an SMD pad, which must be filled and capped, and which at fine pitch is the only escape the geometry permits.

```rust
requires via_in_pad
```

<Callout type="warn">

A requirement is not a permission. It is checked against the `manufacturer` profile's capabilities, and a profile that does not offer the process is an **error**, not a silent downgrade. `jlcpcb`, `pcbway`, and `oshpark` do not offer `via_in_pad`; `manufacturer "jlc-filled-via"` (JLCPCB with the resin-filled via option) does.

</Callout>

Repeat the statement for several processes. Declaring one twice is still one requirement.

## Components

```text
component <RefDes>: <kind> "<part_id>" [value "<display>"] [{ <block> }]
```

| Part          | Meaning                                                    |
| :------------ | :--------------------------------------------------------- |
| `<RefDes>`    | Unique designator on the board: `U1`, `C3`, `R_CC1`.       |
| `<kind>`      | Coarse category — see [Component Kinds](#component-kinds). |
| `"<part_id>"` | Registry key naming the actual part.                       |
| `value "…"`   | Display value for the schematic and BOM.                   |

```rust
component J1:  connector "usb_c_receptacle"
component U1:  regulator "ams1117_3v3" value "AMS1117-3.3"
component R1:  resistor  "r_generic_0603" value "10k"
component C1:  capacitor "c_generic_0603" value "100nF"
component D1:  led       "led_green_0603"
```

<Callout type="warn">

Give every generic passive a `value`. A missing one is an **error** (`E-SYNTH-VALUE-001`), not a warning — `r_generic_0603` names a package, not a resistance, and without a value the BOM is unorderable.

</Callout>

### Reference Designators

Standard EDA prefixes. Synth does not enforce these, but every tool downstream expects them:

| Prefix    | Type                 | Prefix | Type               |
| :-------- | :------------------- | :----- | :----------------- |
| `C`       | Capacitor            | `Q`    | Transistor         |
| `D`       | Diode / LED          | `R`    | Resistor           |
| `J`       | Connector            | `SW`   | Switch             |
| `L`       | Inductor             | `U`    | Integrated circuit |
| `Y` / `X` | Crystal / oscillator | `FB`   | Ferrite bead       |

### Component Kinds

The kind is the part's coarse electrical category. Kinds present in the shipped registry:

`antenna` · `buzzer` · `capacitor` · `charger` · `connector` · `crystal` · `diode` · `display` · `filter` · `fuse` · `ic` · `inductor` · `led` · `level_shifter` · `mcu` · `memory` · `modem` · `opamp` · `regulator` · `resistor` · `secure_element` · `sensor` · `switch` · `transistor`

### Part IDs and Pin Names

The part ID maps to a `.synth.toml` entry in the [component registry](/user-guide/registry-and-fixtures), which is also where pin names come from. `connect U1.vout` only works because the registry entry for `ams1117_3v3` declares a pin called `vout`.

```bash
synth registry list        # every available part ID
```

Do not guess pin names — look them up. A misspelled pin is `E-SYNTH-COMP-002` (undefined pin); a misspelled reference designator is `E-SYNTH-COMP-004`; an unknown part ID is `E-SYNTH-COMP-001`, which helpfully suggests the three closest matches in the registry.

## Connections

```text
connect <RefDes>.<pin> -> <RefDes>.<pin> [as "<NET_NAME>"]
```

Each statement joins two pins onto one electrical net. To put more than two pins on a net, repeat `connect` and reuse the net name:

```rust
connect U1.gnd -> C1.p2 as "GND"
connect U1.gnd -> C2.p2 as "GND"
connect U1.gnd -> U2.vss as "GND"   // all four pins, one GND net
```

<Callout type="info">

Always name your nets with `as "…"`. A named net renders its name as the schematic label; an unnamed one is auto-named `net_7`, and `E-SYNTH-SCHEM-014` flags it when it reaches the sheet. Net names should be `UPPERCASE` and 16 characters or fewer (`E-SYNTH-SCHEM-008` / `-009`).

</Callout>

## Named Nets

Declare a net explicitly, optionally listing its member pins, and optionally assigning it a netclass:

```text
net "<NAME>" [class "<netclass>"] [{ <RefDes>.<pin>* }]
```

```rust
net "I2C_SCL" class "I2C" { U1.scl U2.pb6 }
```

This is an alternative to `connect … as`, useful when you would rather list a bus's members in one place than scatter `connect` statements.

## Power Rails

```text
power "<RAIL>" <value><unit> [class "<netclass>"] [{ <RefDes>.<pin>* }]
```

```rust
power "+3V3" 3.3v
power "+5V"  5v { U1.vin C1.p1 }
```

Rails differ from ordinary nets in two ways that matter:

- They render as **power symbols** on the schematic rather than drawn wires, which removes a great deal of visual clutter.
- The declared voltage feeds the voltage-domain ERC rules, instead of Synth guessing a rail's voltage from pin names.

A bare declaration still creates the net, so later `connect … as "+3V3"` statements join it.

## Groups

```text
group "<title>" [color "#rrggbb"] [title "<display>"] [region <region>] { <statement>* }
```

This is the single most important statement for schematic readability. A group becomes a titled, coloured, dashed box on the sheet; its members are placed together inside it; nets that stay inside are drawn as wires, while nets crossing out become labels.

```rust
group "3V3 LDO" color "#c2410c" {
  component U2: regulator "ap2112k_3v3" value "AP2112K-3.3"
  component C5: capacitor "c_generic_0603" value "100nF"
}
```

| Attribute           | Effect                                             |
| :------------------ | :------------------------------------------------- |
| `color "#rrggbb"`   | Overrides the deterministic palette hue.           |
| `title "<display>"` | Display title different from the identifier.       |
| `region <region>`   | Steers which page quadrant the group packs toward. |

<Callout type="warn">

An ungrouped board lays out as one flat band and is effectively unreadable past a handful of parts. Aim for **3–6 groups** named after functional blocks — power input, MCU, sensors, connectors. Reference designators stay board-unique regardless of group, and `connect` may cross group boundaries freely.

</Callout>

## Notes

```text
notes "<title>" { "<line>"* }
```

Free prose rendered on the sheet. Inside a `group` it is drawn at the bottom of that group's box; at board level it stacks below all content. Pass `""` as the title for an untitled block.

```rust
notes "" {
  "I2C address 0x76 (SDO tied low); CSB high selects I2C."
  "4.7k bus pull-ups sized for 400 kHz at 3.3 V."
}
```

Use it for the intent a netlist cannot carry: I²C addresses, strap choices, current budgets, assembly notes. `E-SYNTH-SCHEM-015` reminds you when a group has none.

## Placement Hints

Guide the auto-placer from inside a component declaration. Every attribute is optional and independent — include only what you need.

```text
component <RefDes>: <kind> "<part_id>" {
  placement_hint { region: <region> edge: <edge> near: <RefDes> side: <side> priority: <hard|soft> }
}
```

```rust
component U1: mcu "rp2350" {
  placement_hint { region: top_left priority: hard }
}

component C4: capacitor "c_generic_0603" value "100nF" {
  placement_hint { near: "U2" priority: hard }
}
```

| Attribute  | Accepted values                                                                                                                |
| :--------- | :----------------------------------------------------------------------------------------------------------------------------- |
| `region`   | `top_left` · `top_right` · `bottom_left` · `bottom_right` · `centre` · `top_edge` · `bottom_edge` · `left_edge` · `right_edge` |
| `edge`     | `top` · `bottom` · `left` · `right`                                                                                            |
| `near`     | Another component's reference designator                                                                                       |
| `side`     | `above` · `below` · `left` · `right`                                                                                           |
| `priority` | `soft` (a preference) · `hard` (pins the component; the solver may not move it)                                                |

<Callout type="info">

Note the spelling `centre`, not `center`. An unrecognised region value is a parse error.

</Callout>

## Pin Escape

Controls how a package's pins leave it.

```text
component <RefDes>: <kind> "<part_id>" {
  escape { [method <channel|underpad>] [layers "<layer>", …] [off] }
}
```

A dense grid array — three or more pad rows and columns at or below 1.3 mm pitch — is escaped before routing whether or not you say so, because a fine-pitch array handed to a general router comes back with a stub on every lane. This block overrides that default.

```rust
component U1: ic "ice40hx4k_bg121" {
  escape { method underpad layers "In1.Cu", "In2.Cu" }
}
```

| Setting           | Meaning                                                                             |
| :---------------- | :---------------------------------------------------------------------------------- |
| `method underpad` | Drops a via inside each pad. The only method a fully populated array leaves open.   |
| `method channel`  | Routes out between the pads.                                                        |
| `layers "…"`      | Limits which copper the escape may use.                                             |
| `off`             | Leaves the package to the general router. Wins over a `method` on the same package. |

The escape via is sized from the declared manufacturer's floor, not from this block.

## Net Classes

```text
netclass "<name>" {
  [trace_width <value><unit>] [clearance <value><unit>]
  [via_diameter <value><unit>] [via_drill <value><unit>]
  [layers "<layer>", …] [color "#rrggbb"]
}
```

Nets are auto-classified (Power, Ground, I2C, SPI, UART, USB, Clock, Reset) and coloured from a fixed palette. A declared class joined with `class "<name>"` overrides both.

```rust
netclass "PWR" {
  trace_width 0.4mm
  clearance 0.25mm
  color "#d55e00"
}
```

`layers` pins the class's nets to specific KiCad copper layers (`"F.Cu"`, `"In1.Cu"`, `"B.Cu"`): the router keeps them there, the export writes it as a KiCad custom rule, and copper anywhere else is `E-SYNTH-DRC-023`. Pinning a controlled-impedance pair to outer layers is how you clear `W-SYNTH-IMPEDANCE-001`.

## Differential Pairs

```text
diff_pair <NET_P> <NET_N> { impedance <value><unit> }
```

Marks two already-connected nets as a differential pair with a target characteristic impedance.

```rust
connect J1.dp -> U1.usb_dp
connect J1.dn -> U1.usb_dn

diff_pair U1_usb_dp U1_usb_dn {
  impedance 90ohm
}
```

<Callout type="info">

There is no separate net-naming syntax for pairs. Each leg is written `<REFDES>_<pin>` and matched against any net having that component and pin as an endpoint — which also means a pair's legs must be reachable this way. If a net was auto-named and has no identifying endpoint, name it with `as "…"` first.

</Callout>

## Keepout Zones

```text
keepout <name> { radius <value><unit> }
```

A circular region the router must avoid — under an antenna, for instance.

```rust
keepout antenna { radius 15mm }
```

## Stackup

Declares the board's physical layers from top to bottom. Copper and insulator entries alternate, starting and ending with copper.

```text
stackup { copper <t><unit> | insulator <t><unit> er <number> [material "<name>"] ... }
```

```rust
stackup {
  copper 0.035mm
  insulator 1.5mm er 4.4 material "FR4"
  copper 0.035mm
}
```

The number of copper entries must equal `layers` (`E-SYNTH-STACKUP-001`). `er` is the insulator's dielectric constant, a plain number. The exporter writes the stack into the `.kicad_pcb` stackup section and sets board thickness to the stack total.

<Callout type="info">

Synth ships no fabricator presets and no default stack. Omit the block and the board exports with the exporter's default thickness and no stackup section at all — which is fine until you need controlled impedance.

</Callout>

## Build Variants

```text
variant "<name>" [description "<text>"] { dnp <RefDes>* }
```

One schematic and one layout, with some parts left unpopulated.

```rust
variant "lite" description "No radio" { dnp U3 U4 }
```

Exports as KiCad 10 native variants plus a `bom.<variant>.csv` per variant. ERC still checks parts marked do-not-populate.

## Hierarchical Sheets

```text
sheet "<name>" { <statement>* }
```

Statements lower exactly as in a `group` — reference designators stay board-unique and cross-sheet `connect` is allowed — but the name is also a split point. A board whose single-sheet content overflows A2 **and** which has two or more populated boundaries exports as a KiCad hierarchy, one file per sheet. Small boards stay on one page.

```rust
sheet "Power" {
  component U1: regulator "ams1117_3v3" value "AMS1117-3.3"
}
```

## Modules

Reusable parameterised sub-circuits, for when a block repeats.

```text
module <Name> [( <param> = <default>, … )] { port <Port>: <interface>  <statement>* }
interface <Name> { <signal>* }
bus <Name> { <member>* }
use <Module> as <Prefix> [( <param> = <value> )]
bind <Prefix>.<Port> -> <target>
```

```rust
interface Gpio { sig }

module LedBank(count = 3) {
  port ctrl: Gpio
  component R1: resistor "r_generic_0603" value "1k"
}

use LedBank as LB1 ( count = 4 )
bind LB1.ctrl -> "GPIO2"
```

| Keyword     | Role                                                       |
| :---------- | :--------------------------------------------------------- |
| `module`    | Defines the sub-circuit and its parameters.                |
| `port`      | A connection point on the module, typed by an `interface`. |
| `interface` | Names a bundle of signals a port can carry.                |
| `bus`       | Groups member nets under one name.                         |
| `use`       | Instantiates a module under a reference-designator prefix. |
| `bind`      | Wires an instance's port to a net or interface.            |

## Imports

```text
import "<relative/path.synth>"
```

Inlines another file's statements at that point. Paths must be relative, contain no `..` segments, and resolve from the importing file's directory. Import cycles are rejected.

```rust
import "common/power_tree.synth"

board "my_board" {
  layers 2
}
```

## Units

A numeric literal takes an explicit unit suffix. These are the **only** accepted units:

| Quantity    | Units                   |
| :---------- | :---------------------- |
| Length      | `mm` · `mil`            |
| Resistance  | `ohm` · `kohm` · `mohm` |
| Voltage     | `v` · `mv`              |
| Current     | `a` · `ma`              |
| Frequency   | `mhz` · `ghz`           |
| Capacitance | `pf` · `nf` · `uf`      |

```rust
radius 8mm
impedance 90ohm
power "+3V3" 3.3v
```

<Callout type="warn">

`um`, `in`, `cm`, `hz`, and `khz` are **not** valid units and produce `E-SYNTH-PARSE-023`. Note also that these units apply to _numeric literals_; the `value "100nF"` on a component is a free-form display string, which is why it is quoted.

</Callout>

## Comments

Both forms are supported. Block comments do not nest.

```rust
// Line comment, to end of line

/* Block comment,
   across several lines */
```

## String Escapes

Strings accept `\\`, `\"`, `\n`, `\t`, and `\r`.
